# 教学游戏架构改进 PRDs

状态：需求草案，尚未实施。更新：2026-11-07。

这组 PRD 将架构审查转化为可拆分、可验收的工程需求。目标是降低关卡制作成本，让地图提示与真实行为一致，并减少进度处理的遗漏。具体 interface、数据结构和文件拆分留到技术设计阶段确定。

## 实施顺序

| 顺序 | PRD | 交付结果 | 依赖 |
| --- | --- | --- | --- |
| 1 | [PRD-01 关卡定义与场景编制](PRD-01-关卡定义与场景编制.md) | 一处确定每关、每个场景的最终内容，生成内容与目录一致 | 无 |
| 2 | [PRD-02 地图交互与执行规则统一](PRD-02-地图交互与执行规则统一.md) | 点击帮助给出的可执行条件与实际执行一致 | 可独立启动；与 PRD-01 对齐最终关卡数据 |
| 3 | [PRD-03 学习进度生命周期](PRD-03-学习进度生命周期.md) | 提交、切换、修订失效和保存遵循完整规则 | 可独立启动；需使用稳定的关卡与场景身份 |

默认按 01 → 02 → 03 小批实施。若课堂已复现提示与执行冲突，可先交付 02 的守卫交互试点。每项完成独立验收后再扩大范围。

## 共同约束

- 关卡以真实游戏结果验收，不恢复“不使用指定语句就不给过”的限制。
- 鼠标点击地图仅查看帮助。代码明确指定目标；全局查询与需要接近的交互继续区分。
- 保留当前 `wait()` 默认 1 秒、支持整数参数，以及游戏时钟和循环的既定语义。
- 保留已有登录、教师显隐与开放控制、关卡前置依赖、自动入场对白和去重提示。
- 用户允许调整关卡，无需无限兼容历史地图；但学生账号、保存代码和已有学习记录不得因结构重构被静默删除。关卡内容修订需要单独声明是否使通过记录失效。
- 每项 PRD 只规定需求和验收，文中的实施方向不是已确定的技术 interface。
- 本轮交付为文档；实现、发布与推送尚未执行。

## 验收原则

1. 先保存实施时的工作区基线，包括未提交的关卡改造；不能用旧提交替代当前教学行为。
2. 对可观察结果做测试：最终地图、交互结果、完成记录和下一步位置；不以内部函数数量、文件数量或行数作为成功标准。
3. 先建立完整行为测试，再替换被覆盖的重复测试；保留真实浏览器和引擎的必要验证。
4. 不引入没有实际用途的通用 adapter、第二种游戏引擎或第二种存储。
5. 涉及存储的验证使用临时数据目录，涉及部署的验证使用隔离环境。

审查基于 `26e29c0` 及 2026-11-07 工作区，通过静态阅读与独立复核得到。未在本次文档编写中重新运行游戏测试。文件位置是当时的导航线索，后续实现可能变化。

- `teaching/map-inspection.js` 与 `teaching/rules-system.js`：守卫距离提示与隔墙执行检查存在规则差异；尚未证明现有布局会实际触发。
