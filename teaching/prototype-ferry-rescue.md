# 渡口最后一班船：可丢弃逻辑原型

打开同目录 `prototype-ferry-rescue.html` 即可使用；无服务器、依赖、外链或持久化。原型仅在 `codex/prototype-ferry-rescue` 分支保存，不进入正式关卡目录或教学分支。

## 设计问题

通过同一个世界中的两种任务，能否让学习者体会“重复已知次数”与“观察变化直到任务完成”的区别，而不靠强制语法验收？先领取三块材料，点亮三盏灯，使航道可通行；再运送分批抵达的村民，直到收到收队信号且无人滞留。

## 如何体验

- 先点击“开始时间”，用右侧六个动作自由尝试。每个动作都改变可见状态，世界时间独立推进。
- 也可暂停，逐秒推进，或运行低代码方案。示意代码不可直接用于正式游戏，本页不是 Python 解释器。
- 下方五个情境标签提供逐步可点击演示；切换标签会重置并暂停。
- 优先体验第③项：固定三次发船结束后，仍有一位村民滞留；第④项：同一观察方案接应迟到者。固定次数允许调整，足够次数同样可完成，不因使用 for 判失败。
- 教师展开完整状态，可看到确定的到达安排。重跑同一情境完全一致；时间加速按钮仅供观察。

## 本次观察与未验证内容

2026-11-08：在本机 Chrome 实际点击五个引导演示，观察到正常接应、空码头拒绝发船、固定次数结束仍有人滞留、持续观察接应迟到者、无人场景等待确认。修复灯后材料消耗、航道开启与村民出现有关联。已查看桌面及窄屏布局。另在界面把固定次数调为20次，观察到4位村民全部安全抵达并完成任务，确认没有语法排他性判定。

这些只能说明模型能表达上述情况，不能证明学生会自发想到循环，也不能证明足够有趣。待教师和学生试玩判断：任务能否看懂？如何解释空码头与完成的差别？方案改动能否迁移到另一种到达情况？是否愿意继续尝试？本轮不将任何未经确认的决定并入生产代码。

边界：无战斗或生命惩罚、没有真实 Python 运行器、没有生产游戏美术与移动动画；使用静态示意图聚焦因果关系。所有状态只在内存中。纯逻辑位于第一个 script 块，页面及方案调度位于第二块。

## 第二版：依据用户反馈改造直接引导

用户对第一版的反馈：“有点抽象，好像没有什么直接的反馈引导我去做这些事情。”因此第一版不能视为已经验证了可理解性。

第二版保留纯状态模型，改造体验入口：船夫先提出航灯熄灭的具体困难；当前物件有单一箭头；眼前的一步有明确按钮与对应命令。点击物件只查看帮助，执行仍需下达动作。动作自动启动世界时间，不需要先理解“开始时间”开关。

材料领取后背包填充；装填后插槽填满、航灯点亮、电线接通，显示前后数量。错误发船在场景对白中解释原因。村民实际出现在岸边、渡船座位和安全岛；收队旗与待接人数共同决定完成。空码头只说明山路尚未确认清空，不断言还有人。完整状态与固定到达表保留在教师观察面板；五个逐步情境仍可展开。

本机Chrome已实际点击未修灯发船、领取、移动和装填，查看场景反馈；五个引导情境仍可走通，窄屏未出现页面横向溢出。尚待用户再次体验，不能把新增提示等同于学生已理解。正式教学分支保持不变。
